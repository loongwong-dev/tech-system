# 代码评审

评审的对象是「代码构建得是否良好」，与「需求是否交付」分开判断。

- **类型**：通用规范
- **覆盖范围**：评审维度、逻辑自洽检查、评论格式、评审动作、规模控制、合并条件。
- **不覆盖范围**：任务与验收见 [Issue 驱动开发流程](issue-workflow.md)；项目特有的检查见 [设计文档](../design/README.md)。
- **状态**：已定，评审方法变化需同步 PR 模板。

## 1. 评审维度

源自 Google 工程实践的评审清单，八项，长期稳定。

| 维度 | 要问的问题 |
| --- | --- |
| 设计 | 职责是否清晰？是否与既有结构一致？是否放错了层？ |
| 功能 | 是否真的实现了意图？错误路径、并发、边界是否成立？ |
| 复杂度 | 能否更简单？是否提前抽象了尚不需要的东西？ |
| 测试 | 断言的是行为还是实现？代码坏了测试会红吗？失败路径有覆盖吗？ |
| 命名 | 名字能否独立表达含义，而不依赖上下文？ |
| 注释 | 是否中文？解释的是「为什么/约束」还是「做什么」？公开接口与复杂分支是否覆盖？ |
| 风格 | 交给工具，人只处理工具覆盖不到的一致性 |
| 文档 | 行为、配置、接口变化是否同步了对应文档 |

补充两条 Google 明确要求的习惯：

1. **看完整上下文**，不只看 diff 附近的几行。四行新增可能落在一个已经过长的函数里。
2. **不接受降低代码健康度的改动**。系统是被大量小改动拖垮的。

## 2. 逻辑自洽三问

功能正确不等于逻辑自洽。评审时固定问这三句：

| 问题 | 检查什么 |
| --- | --- |
| 不变量 | 哪些条件必须恒成立？代码在哪里保证？有没有绕过路径？ |
| 状态转换 | 非法状态是否被拒绝？进程中断后能否从任意状态恢复？ |
| 边界 | 空、零、负、超限、并发、超时、部分成功分别会怎样？ |

第三问覆盖了绝大多数线上事故：不是主流程写错了，而是某个边界没有定义行为。

## 3. 评论格式

采用 Conventional Comments，让严重级别可读、可检索：

```text
<label> [(decoration)]: <subject>

[说明与建议]
```

| 标签 | 用途 |
| --- | --- |
| `issue:` | 明确的问题，通常附建议 |
| `suggestion:` | 改进方向，作者可判断 |
| `todo:` | 小但必须改的事项 |
| `question:` | 有疑虑但不确定是否成立 |
| `nitpick:` | 纯偏好，天然非阻断 |
| `thought:` | 评审中想到的点子 |
| `praise:` | 值得肯定的做法 |

装饰项：`(blocking)`、`(non-blocking)`、`(if-minor)`。

约定：默认**阻断**，非阻断必须显式标注 `(non-blocking)`。项目如有例外，在评审约定中写明。

评审结论只有三种：`Approve`、`Request changes`、`Comment`。

## 4. 评审动作

按顺序执行：

1. 读 Issue 的验收标准与完成定义，确认这次改动在解决什么问题。
2. 看变更规模，判断是否需要拆分。
3. **实际运行**受影响路径；只有文档改动可以跳过。
4. 按第 1 节八个维度逐项过一遍，逐行阅读核心逻辑。
5. 用第 2 节三问检查逻辑自洽。
6. 抽查测试有效性：临时改坏一处实现，确认对应测试变红。
7. 给出结论。

第 6 步是发现「永远绿的测试」的唯一手段，不可省略。

## 5. 规模

| 净变更 | 处理 |
| --- | --- |
| ≤ 200 行 | 正常评审 |
| 200–400 行 | 需说明为何不能再拆 |
| > 400 行 | 拆分；机械改动（重命名、生成物、纯文档）除外 |

超过 400 行后，评审质量会明显下降——后半部分往往只是浏览。规模本身不是问题，**「读不完所以没读」才是**。

## 6. 合并条件

全部满足才可合并：

1. CI 全绿。
2. 维护者给出 `Approve`。
3. Issue 的验收标准逐条附有证据。
4. 所有 `blocking` 评论已解决。
5. PR 正文包含 `Closes #N`。
6. 分支基于最新 `main`。
7. 迁移、配置或部署影响已说明。

AI 不得执行合并或启用自动合并；合并只能由维护者授权。

## 7. AI 生成的改动

AI 的失败模式与人类不同，评审时重点看这几类：

| 失败模式 | 表现 | 检查动作 |
| --- | --- | --- |
| 看似合理但未验证 | 代码能编译，实际路径跑不通 | 必须实际运行 |
| 测试空转 | 有测试，但断言恒真 | 改坏实现看是否变红 |
| 重复实现 | 已有工具函数，又写了一份 | 搜索同名能力 |
| 过度抽象 | 为单一调用点引入 trait 或配置项 | 问「现在需要吗」 |
| 幻觉 API | 调用了不存在的函数或参数 | 以编译与官方文档为准 |
| 超出范围 | 顺手改了无关文件 | 对照 Issue 的非范围 |

## 8. 反模式

| 反模式 | 后果 |
| --- | --- |
| 只看 CI 是否绿 | 机器检查覆盖不到逻辑与设计 |
| 只读 diff 不运行 | 无法发现「能编译但不工作」 |
| 用个人偏好阻断 | 评审退化为争论 |
| 大 PR 一次审完 | 后半部分实际没看 |
| 把「以后再说」当结论 | 问题没有落成 Issue |
