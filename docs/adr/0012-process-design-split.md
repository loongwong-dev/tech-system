# ADR-0012：文档按性质拆分通用流程与本项目设计

- 状态：Superseded by [ADR-0014](0014-module-docs-layout.md)
- 日期：2026-10-31
- 决策者：仓库维护者
- 相关：[文档索引](../README.md)、[ADR-0006](0006-docs-structure.md)

## 背景

ADR-0006 把业务文档按主题分为 `product/`、`engineering/`、`ops/`。实际使用后 `engineering/` 同时承载两类内容：

- 与业务无关的工作方式：评审、测试、代码规范、任务流程。
- 只属于本项目的事实：库表、接口、认证、前端结构。

读者无法从路径判断「这份文档换一个项目还成不成立」，通用规范中也混入了项目专有的检查条目。

- 约束 1：单人维护，分类规则必须一句话说清。
- 约束 2：文档头部要能自证性质，单独打开也能判断。
- 不做什么：不按 Diátaxis 四类拆分，本项目规模不需要四层。

## 决策

1. 新增 `docs/process/`，放与业务无关的通用规范：任务流程、代码评审、代码规范、测试策略。
2. `engineering/` 更名为 `design/`，只放本项目设计：数据库、接口、认证、前端。
3. 每份文档头部增加「类型」字段：模板治理、通用规范、项目需求、项目设计、项目运维。
4. 项目特有的检查从通用文档移出，集中到 `design/README.md` 的「评审关注点」表。
5. 判断归属的统一问题：**换一个项目，这份内容还成立吗？**

## 后果

### 正面

- 从路径即可判断文档性质，不需要打开。
- 通用文档保持稳定，项目变化只影响 `product/`、`design/`、`ops/`。
- 项目检查与其所属领域放在一起，新增功能时不用改通用标准。

### 负面 / 代价

- 目录多一层，链接需要同步更新，迁移一次性成本较高。
- `code-standards.md` 与 `testing.md` 仍包含少量项目取值（crate 名、sqlx 用法），无法完全通用化。
  → 已由 [ADR-0013](0013-design-engineering-standards.md) 将两份文档归入 `design/`。
- 历史决策中出现的旧路径不会自动更新。

### 风险与缓解

- 风险：通用文档再次混入项目细节。
  缓解：文档头部标注类型；新增项目检查时先问归属。
- 风险：迁移遗漏链接。
  缓解：`check.sh docs` 校验全部站内链接。

## 备选方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 维持 `engineering/` 混合 | 迁移成本为零 | 性质混淆持续存在 | 正是要解决的问题 |
| 仅加「类型」字段不改目录 | 成本最低 | 路径仍无信息量，查找靠记忆 | 只解决一半 |
| 按 Diátaxis 四类拆分 | 分类理论完整 | 对单人项目过细，边界争议多 | 收益不足 |

## 验证方式

- 命令或检查项：`bash scripts/check.sh docs`；任意文档单独打开时能从头部判断类型。
- 观察指标：新增文档时是否需要反复讨论归属。
- 复核时间：下一次新增文档主题时。
