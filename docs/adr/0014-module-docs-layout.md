# ADR-0014：文档按性质与功能模块组织

- 状态：Accepted
- 日期：2026-10-31
- 决策者：仓库维护者
- 相关：[文档索引](../README.md)、[流程规范](../process/README.md)、[产品文档](../product/README.md)、[设计文档](../design/README.md)

## 背景

文档组织经历了三次调整：

- ADR-0006 按主题分层，并引入目录级索引。
- ADR-0012 把 `engineering/` 拆成通用的 `process/` 与本项目的 `design/`。
- ADR-0013 把项目特有的代码与测试规范归入 `design/`。

三次调整都是有效决策，但留下了两条同时有效的路径规则和四份历史文件。当前需要把「现行规则」收敛到一条 ADR：

- 当前只有课后反馈一个业务模块，文件按文档类型命名，无法从路径看出属于哪个模块。
- 后续会加入课件资源等模块；`requirements.md`、`database.md`、`frontend.md` 这类通用文件名会在同一层冲突。
- 模块专有内容与跨模块的平台规则混在同一目录，新增模块时只能继续往同一层堆文件。

- 约束 1：模块边界必须从路径直接可见，不能依赖文件名前缀。
- 约束 2：跨模块的工程规范与系统契约仍要只有一个权威位置。
- 约束 3：历史决策不删除，但同一主题只保留一条现行 ADR。
- 不做什么：不为未来模块预建空目录；不把全系统共享的数据库与 API 契约拆成多份。

## 决策

1. `docs/` 根目录只保留模板治理文档；与业务无关的流程放 `process/`。
2. `product/` 按模块组织：
   - `platform/`：跨模块的平台规则（租户、权益、管理端、合规、里程碑）。
   - `<module>/`：模块需求与冷启动，当前为 `feedback/`。
3. `design/` 分三层：
   - `engineering/`：跨模块的代码规范与测试策略。
   - `platform/`：全系统共享契约（认证、数据库、API、前端壳）。
   - `<module>/`：模块专有设计，当前为 `feedback/`。
4. 索引采用 README 链：`docs/README.md` 只索引各目录的 `README.md`，各层 `README.md` 逐级索引；`check.sh docs` 校验整条链。
5. 文件名使用固定主题名，目录表达模块归属：
   - 模块需求：`requirements.md`、`launch.md`。
   - 模块设计：`prompt.md` 等模块专有主题。
   - 平台与工程：`authentication.md`、`database.md`、`api-contract.md`、`frontend.md`、`code-standards.md`、`testing.md`。
6. 不再给文件名加模块前缀；模块内新增主题先在模块 `README.md` 登记。
7. 全系统的表结构、API 与前端壳保留在 `platform/`，模块 `README.md` 只给章节映射，不复制正文。
8. 可从代码推导的事实以生成物为准：表结构与索引以迁移文件为准，接口字段以 `openapi.json` 为准，文档只保留原则与约定。

## 后果

### 正面

- 从路径即可看出文档属于哪个模块，新模块按同一结构扩展。
- 跨模块规范与模块规则分开，评审时不需要在通用文档里找项目取值。
- 固定主题名减少命名分歧，链接稳定。
- 文档组织只有一条现行 ADR，读者不需要沿编号链回溯。

### 负面 / 代价

- 目录深一层，迁移一次性成本较高。
- `platform/` 文档包含当前模块的表与端点，模块读者需要经 `README.md` 跳转。
- 模块增多后，`design/platform/` 可能继续变大，需要按契约类型再拆。
- 历史 ADR 仍保留，首次阅读需要经主题索引区分现行与历史。

### 风险与缓解

- 风险：新模块把平台级规则复制到自己目录。
  缓解：模块 `README.md` 只链接平台章节；评审检查重复事实。
- 风险：移动文件导致链接断裂。
  缓解：`bash scripts/check.sh docs` 校验全部站内链接与 README 索引链。
- 风险：为未来模块预建空目录。
  缓解：只在模块真正开始时创建目录与 `README.md`。

## 备选方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 平铺 + 模块名前缀 | 无目录层级 | 文件数增长后难以浏览，前缀重复 | 路径无法表达模块 |
| 保持现状，后续再拆 | 零迁移成本 | 新增模块时冲突更严重 | 模块已在规划中 |
| 按数据库、API、前端拆每个模块 | 模块边界最彻底 | 全系统契约被切碎，跨模块查询困难 | 单一数据库与 API 不适合切分 |

## 验证方式

- 命令或检查项：`bash scripts/check.sh docs`；`docs/product/` 与 `docs/design/` 下不存在旧平铺路径；同一主题只有一条 `Accepted` 的现行 ADR。
- 观察指标：新增模块时是否需要修改既有目录结构。
- 复核时间：第二个业务模块启动时。

## 修订记录

- 2026-10-31：补充后续新增模块只按本结构扩展，不再为目录结构新增 ADR；依据 [ADR-0015](0015-adr-revision-policy.md)。
- 2026-10-31：吸收 ADR-0006、ADR-0012、ADR-0013 的现行规则（`process/` 归属、目录索引链、生成物权威、代码与测试规范位置），三者标记 `Superseded by`；本文成为文档组织的唯一现行决策。
