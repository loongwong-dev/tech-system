# ADR-0007：C 端采用响应式 Web，暂不做小程序

- 状态：Accepted
- 日期：2026-10-31
- 决策者：仓库维护者
- 相关：[ADR-0005](0005-two-frontends.md)、[需求说明](../product/requirements.md)、[认证与安全](../engineering/authentication.md)

## 背景

教师主要在课后用手机录入，产品是移动优先的。同时存在三个约束：

- 目标用户通过微信群等私域渠道获取，链接触达是主要方式。
- 未来可能增加课件资源市场，主场景是教师在电脑上查找与下载。
- 单人维护，无法同时承担三套前端（C 端、管理端、小程序）。

- 不做什么：不做原生 App，不做小程序与 Web 的并行双端实现。

## 决策

C 端采用**响应式 Web**，手机优先，同时预留桌面布局。

1. 断点：`< 768px` 单列；`768–1023px` 单列宽屏；`>= 1024px` 双列。
2. 核心链路不绑定浏览器专属能力；离线草稿优先 IndexedDB，并保留 localStorage 降级路径。
3. 家长分享页保持独立的服务端渲染 HTML，对 H5、小程序与短信均中立。
4. 小程序后置，若确需上线，优先做 web-view 壳复用现有 H5，不重写业务。
5. 登录采用邮箱加密码，配合 30 天滑动会话，把移动端输入频率降到最低。

## 后果

### 正面

- 一套代码覆盖手机与桌面，未来课件市场可以直接长在同一应用里。
- 无小程序审核周期与类目资质前置条件，可随时发布与修复。
- 家长分享页用普通链接，任何环境都能打开。

### 负面 / 代价

- 微信群内点击转化略低于小程序卡片。
- 图片保存依赖长按，无法调用相册写入接口。
- 微信内登录需要手动输入邮箱与密码，首次体验不如授权登录。
- 移动端性能与手势体验上限低于原生。

### 风险与缓解

- 风险：移动端登录摩擦导致注册流失。
  缓解：30 天滑动会话；后续按数据决定是否引入短信或网页授权。
- 风险：分享页在微信内被折叠或拦截。
  缓解：页面体积控制在 2KB 级，标题与摘要完整，避免诱导分享文案。
- 风险：日后必须上小程序，导致返工。
  缓解：断点、API 契约与分享页均已中立化；web-view 壳是低返工路径。

## 备选方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 微信小程序 | 群内转化高、图片可直接保存、登录无摩擦 | 需类目资质与备案，版本审核 1–3 天，无法覆盖桌面端 | 与桌面端需求冲突，且审核制不适合单人快速迭代 |
| H5 + 小程序双端 | 兼顾获客与桌面 | 两套 UI 与发布流程，工作量接近翻倍 | 单人无法承受 |
| Taro / uni-app 跨端 | 逻辑复用 | UI 与包体积约束多，调试复杂 | 收益不足以抵消复杂度 |

## 验证方式

- 检查项：`>= 1024px` 视口下 C 端可用且非拉伸变形；微信内置浏览器完成「录入 → 生成 → 分享」全流程。
- 观察指标：移动端注册完成率、首次分享完成率、桌面端访问占比。
- 复核时间：累计 100 名付费用户后，用数据重新评估是否需要小程序入口。
