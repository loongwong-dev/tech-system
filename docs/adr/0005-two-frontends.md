# ADR-0005：C 端与管理端拆为两个前端应用，契约由后端生成

- 状态：Accepted
- 日期：2026-10-31
- 决策者：仓库维护者
- 相关：[ADR-0001](0001-rust-backend.md)、[需求说明](../product/requirements.md)

## 背景

前端有两个面向完全不同的界面：教师使用的 C 端工作台，以及运营使用的管理后台。两者共享设计语言，但布局、导航、权限模型与发布节奏都不同。后端改为 Rust 后，前后端不再共享语言与 schema 定义。

约束：

- 后端是契约的唯一来源，前端不得手写重复类型。
- 管理端代码不应出现在 C 端的构建产物中。
- 单人维护，构建配置与依赖升级必须尽可能少。

- 不做什么：不做微前端、不做运行时模块联邦、不做 SSR。

## 决策

拆为两个独立的 Vite + React 应用，并共享设计系统与生成的 API 类型。

必须满足的规则：

1. `apps/web` 与 `apps/admin` 各自独立构建、独立产物、同域不同路径部署。
2. 设计系统放在共享包中，两个应用都从中取组件，不复制样式。
3. 后端用 utoipa 产出 OpenAPI，CI 生成 TypeScript 类型并提交；生成结果与后端不一致时 CI 失败。
4. 前端禁止手写接口类型；Zod 只用于表单校验与本地输入约束。
5. 管理端路由必须校验平台角色，前端守卫只是体验，服务端必须独立鉴权。
6. 不引入 SSR 框架。

## 后果

### 正面

- 管理端代码与依赖不会进入 C 端产物，公开包体更小。
- 两个应用的发布节奏解耦。
- 契约方向单一，后端改字段时前端编译即报错。

### 负面 / 代价

- 两套构建配置与应用壳层，升级依赖需要改两处。
- 设计系统包的版本与引用关系需要维护。
- 生成的类型文件会产生 diff 噪音。

### 风险与缓解

- 风险：两个应用逐渐分叉，组件实现重复。
  缓解：共享包只放通用组件；出现第二份实现时先抽取再加功能。
- 风险：生成类型与后端漂移。
  缓解：CI 中重新生成并检查工作区无 diff，漂移即失败。
- 风险：管理端被误配置到公开路径且缺少服务端校验。
  缓解：管理端接口独立路由分组，权限中间件默认拒绝。

## 备选方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 单应用双路由树 | 构建与依赖只维护一份，产物共享 | 管理端代码进入同一构建，权限边界靠路由守卫 | 维护者选择更清晰的边界 |
| Next.js 双应用 | 生态成熟，路由与数据获取内置 | 需要 Node 运行时，与 Rust 后端重复；无 SSR 需求 | 增加部署面 |
| tRPC 式端到端类型 | 类型零生成 | 后端是 Rust，无法共享类型；且需要自建桥接 | 语言不一致 |

## 验证方式

- 命令或检查项：CI 重新生成类型后 `git diff --exit-code`；分别构建两个应用并检查产物互相不包含；未授权访问管理端接口返回 403。
- 观察指标：C 端首屏包体积、类型生成漂移次数。
- 复核时间：M5 上线后两周，以及每次新增跨端共享组件时。
