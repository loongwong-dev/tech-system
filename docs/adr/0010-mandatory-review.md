# ADR-0010：合并前必须人工评审，AI 不得自行合并

- 状态：Accepted（第 3 条由 [ADR-0011](0011-review-standard-separation.md) 修订）
- 日期：2026-10-31
- 决策者：仓库维护者
- 相关：[代码评审](../process/code-review.md)、[Issue 驱动开发流程](../process/issue-workflow.md)、[AGENTS.md](../../AGENTS.md)

## 背景

Issue 流程解决了「任务可见」，但没有解决「合入质量」。AI 生成的改动如果由 AI 自己判断通过并合并，所有门禁都退化为自我声明：

- 机器检查只能覆盖格式、链接、行数、密钥，看不出跨租户越权、错误被吞、测试空转。
- 单人仓库下 GitHub 不允许作者自我批准，缺少明确的替代流程。
- 没有评审标准时，「看着没问题」会成为唯一的判据。

- 约束 1：单人维护，评审必须在几分钟内完成，不能照搬多人团队的流程。
- 约束 2：评审结论必须留在 PR 中，可回溯。
- 不做什么：不引入外部评审工具，不做多级审批。

## 决策

1. 所有改动经 PR 合入 `main`，禁止直接推送。
2. 评审深度按风险分级：A（认证、租户、配额、删除、支付、提示词）、B（业务逻辑、接口、队列、渲染）、C（文档、格式）。
3. 定义 11 条阻断项（CR-01 至 CR-11），存在任一条即 Request changes。
4. **合并只能由维护者执行**，AI 不得调用合并命令。
5. 评审者必须实际运行受影响路径，并抽查测试是否真的会失败。
6. 合并方式统一 squash，保持 `main` 线性。
7. 可跟进项必须开 Issue 记录，不允许口头遗留。

> 修订（同日）：第 3 条的项目专项阻断清单已由 [ADR-0011](0011-review-standard-separation.md) 取代，改为通用评审维度加领域检查单索引。其余决策不变。

因为单人仓库无法自我批准，落地方式是：CI 全绿 + 维护者在 PR 中留下 Approve 结论 + 手动合并，不使用机器人账号绕过。

## 后果

### 正面

- 合并前有一道语义检查，机器检查的盲区被覆盖。
- 风险分级让文档改动不必走完整流程，评审成本可控。
- 阻断项是封闭清单，评审不再是主观判断。

### 负面 / 代价

- 每个 PR 多一次人工介入，无法完全无人值守地推进。
- 阻断项需要维护，新增风险类型时要同步更新。
- 评审必须运行代码，对仅有文档的仓库阶段不构成负担，但实现期会占用时间。

### 风险与缓解

- 风险：评审流于形式，变成看到 CI 绿就 Approve。
  缓解：阻断项逐条核对；A 级必须贴两条测试证据；抽查测试有效性。
- 风险：AI 绕过流程直接推送。
  缓解：`AGENTS.md` A8 明确禁止；分支保护要求 PR 与 CI；发现即回滚并记录。
- 风险：单人维护时评审者与作者是同一人，缺乏独立性。
  缓解：接受这一局限，用「必须实际运行 + 阻断清单」替代第二双眼睛。

## 备选方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 直接推送 `main` | 最快 | 无审查、无记录、无法回滚单次改动 | 与 Issue 追溯链冲突 |
| 仅依赖 CI | 零人工 | 机器检查覆盖不到语义与安全 | 越权与空转测试查不出 |
| 机器人账号自动 Approve | 流程看起来完整 | 自我批准，评审形同虚设 | 违背评审目的 |
| 引入外部代码评审服务 | 自动化程度高 | 额外账户、费用与配置 | 与单人规模不匹配 |

## 验证方式

- 命令或检查项：PR 模板中的自检与评审清单；阻断项逐条核对；`bash scripts/check.sh all` 全绿。
- 观察指标：进入 `review` 后被 Request changes 的比例；合并后 7 天内回滚或修补的比例。
- 复核时间：第一个里程碑完成后，确认阻断项是否过严或遗漏。
