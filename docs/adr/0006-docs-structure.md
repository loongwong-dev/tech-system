# ADR-0006：文档按主题分层并支持目录级索引

- 状态：Accepted
- 日期：2026-10-31
- 决策者：仓库维护者
- 相关：[文档治理与组织](../governance.md)、[文档索引](../README.md)

## 背景

业务文档在几天内从 0 增长到 7 篇，全部堆在 `docs/` 根目录：

- 根目录共 12 篇，模板治理文档与业务文档混在同一层，读者无法从路径判断归属。
- `docs/README.md` 的索引膨胀到 20 条，且每新增一篇文档就线性增加一条。
- `docs/governance.md` 2.6 已经预留了「大」规模形态（目录级索引），但 `check.sh` 只实现了全量索引，两者不一致。
- 更大隐患：文档正在成为代码的第二份副本。表结构与接口字段一旦写进代码，文档必然开始腐烂。

- 不做什么：不引入静态站点生成器，不把文档拆成大量单篇短文。

## 决策

1. `docs/` 根目录只保留模板治理文档：`governance.md`、`ai-behavior.md`、`ci-cd.md`、`configuration.md`。
2. 业务文档按主题归入三个子目录：`product/`、`engineering/`、`ops/`。
3. 每个子目录必须有 `README.md`，`docs/README.md` 只索引目录的 `README.md`，不再逐篇列出。
4. `check.sh` 支持目录级索引：子目录 README 被索引且索引了目录内文件，即视为已登记。
5. 可从代码推导的事实以代码为源：表结构与索引以迁移文件为准，接口字段以 `openapi.json` 为准，文档只保留原则与约定。

## 后果

### 正面

- 索引条目数不再随文档数量线性增长，`docs/README.md` 稳定在 10 条以内。
- 从路径即可判断文档归属，读者少一次猜测。
- 文档与代码的权威边界明确，减少后续同一事实两处维护。

### 负面 / 代价

- 相对链接层级变深，移动文件时容易断链。
- 读者需要多跳一层才能到达正文。
- `check.sh` 逻辑变复杂，约增加 15 行。

### 风险与缓解

- 风险：子目录的 `README.md` 变成新的堆积处，写满摘要。
  缓解：每个子目录 README 只写一行描述加链接，不复制正文。
- 风险：移动文件导致站内链接断裂。
  缓解：`check.sh docs` 会校验全部本地链接，断链即失败。
- 风险：文档继续镜像代码细节。
  缓解：`engineering/README.md` 明确列出以生成物为准的事实清单。

## 备选方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 保持扁平 | 零迁移成本，路径最短 | 根目录与索引持续膨胀 | 已经超出可读范围 |
| 子目录 + 全量索引 | 改动最小，`check.sh` 不动 | 索引仍线性增长 | 只解决一半问题 |
| 合并成单一长文档 | 文件数最少 | 单文件过长，评审与定位都变差 | 违背最小可用原则 |

## 验证方式

- 命令或检查项：`bash scripts/check.sh docs`；新增一篇文档后索引条目不增加。
- 观察指标：`docs/` 根目录 Markdown 文件数（目标 ≤ 5）；`docs/README.md` 链接数（目标 ≤ 10）。
- 复核时间：下次新增文档主题时，确认是否需要第四个目录。
