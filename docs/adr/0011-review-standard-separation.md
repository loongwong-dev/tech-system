# ADR-0011：评审标准与项目规则解耦，专项检查归入领域文档

- 状态：Accepted
- 日期：2026-10-31
- 决策者：仓库维护者
- 相关：[代码评审](../process/code-review.md)、[Issue 驱动开发流程](../process/issue-workflow.md)、[ADR-0010](0010-mandatory-review.md)

## 背景

ADR-0010 曾把 11 条项目专项规则（跨租户测试、禁止 `unwrap`、接口版本等）直接写进评审标准作为阻断项。实施后发现两个问题：

- **重复**：这些规则在 `testing.md`、`code-standards.md`、`api-contract.md` 中已有权威定义，评审标准只是抄了一份，两处容易不一致。
- **不可扩展**：每加一个功能就要往评审标准里补条目。标准本应稳定，却会随项目增长而膨胀，最终没人读。

- 约束 1：评审标准应长期稳定，不随功能变化。
- 约束 2：项目专项检查必须仍然可执行，只是换个归属。
- 不做什么：不取消评审，不降低门槛。

## 决策

把三类问题分开，各归各的机制：

| 问题 | 机制 | 归属 |
| --- | --- | --- |
| 需求是否交付 | 验收标准 + 完成定义 | Issue |
| 代码是否构建良好 | 八项评审维度 | PR 评审 |
| 专项质量是否达标 | 领域检查单与自动化 | 各领域文档与 CI |

具体规则：

1. 评审维度固定为八项：设计、功能、复杂度、测试、命名、注释、风格、文档，来源是 Google 工程实践。
2. 增加「逻辑自洽三问」：不变量、状态转换、边界。
3. 评论格式采用 Conventional Comments 的标签与阻断装饰。
4. 项目专项检查改为**索引**：评审标准只列出「关注点 → 权威文档」，不复制规则。
5. 完成定义（DoD）固定六条，写入 Task 模板，与验收标准分开。
6. 新增功能时，新的专项检查加入对应领域文档，评审标准不动。

## 后果

### 正面

- 评审标准稳定，不随功能增长。
- 规则只有一个权威位置，不会再出现两处不一致。
- 验收与评审分离后，责任清晰：Issue 管「做对了吗」，PR 管「做好了吗」。

### 负面 / 代价

- 评审者需要跳转到领域文档查阅具体规则，多一次点击。
- 索引表本身需要维护，新增领域文档时要补一行。
- 「专项检查」不再集中在评审页，可能被忽略。

### 风险与缓解

- 风险：评审者只按八项看，漏掉项目硬约束。
  缓解：PR 模板保留「已实际运行」与「抽查测试」两项硬要求；CI 覆盖可自动化的部分。
- 风险：索引失效，指向不存在的章节。
  缓解：`check.sh docs` 校验站内链接，断链即失败。

## 备选方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 保留项目阻断清单 | 集中、直接 | 与领域文档重复，随功能膨胀 | 正是要解决的问题 |
| 完全依赖自动化检查 | 零人工 | 逻辑自洽与设计无法自动化 | 覆盖面不足 |
| 引入外部评审工具 | 结构化 | 额外依赖与配置 | 单人规模不匹配 |

## 验证方式

- 命令或检查项：PR 模板中八项维度与三问均已勾选；`bash scripts/check.sh docs` 通过。
- 观察指标：评审标准文档的改动频率（目标：季度级）。
- 复核时间：第二个里程碑完成后，确认专项检查是否被漏看。
