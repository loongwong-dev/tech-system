# ADR-0004：多租户隔离采用应用层约束 + PostgreSQL RLS 双连接池

- 状态：Accepted
- 日期：2026-10-31
- 决策者：仓库维护者
- 相关：[ADR-0001](0001-rust-backend.md)、[平台需求](../product/platform/requirements.md)

## 背景

平台是多租户 SaaS，教师个人或机构各自为租户。一旦出现跨租户读取，等同于泄露未成年人个人信息，属于不可接受的事故。

约束：

- 首年租户 ≤ 300，共享数据库足够，不需要分库或分 schema。
- 开发者只有一人，不能依赖「记得加 where 条件」。
- 管理端需要跨租户查询，这是合法需求，必须与租户查询明确区分。

- 不做什么：不做按租户分库、不做独立 schema、不引入外部授权服务。

## 决策

采用**应用层类型约束 + 数据库层 RLS** 的双层设计。

必须满足的规则：

1. 数据库存在两个角色：`app_tenant`（受 RLS 约束）与 `app_admin`（`BYPASSRLS`）。
2. 进程维护两个连接池，租户路由只能取到租户池，管理端路由只能取到管理池。
3. 租户事务开始后立即执行 `SET LOCAL app.tenant_id = $1`，事务结束自动失效，避免连接回池后泄漏身份。
4. RLS 策略使用 `current_setting('app.tenant_id', true)`，缺失时返回空集而不是报错或全表。
5. 业务查询**仍然保留** `WHERE tenant_id = $1`：索引依赖它，安全由策略兜底。
6. 跨租户表（`users`、`tenants`、`invite_codes`、平台模板）不启用 RLS，只能经由管理池访问，并维护一份显式例外清单。
7. 迁移与 DDL 由表所有者角色执行，与应用角色分离。

## 后果

### 正面

- 遗漏租户条件时，最坏结果是一条数据都查不到，而不是查到别人的数据。
- 应用层类型把「用错池」变成编译错误。
- 例外清单明确，审计时能直接对照。

### 负面 / 代价

- 所有租户查询必须在事务中执行，代码比裸查询更啰嗦。
- 需要维护两套连接池与两条迁移路径（DDL 与应用角色）。
- RLS 策略本身也是代码，需要测试覆盖。
- 排查问题时必须同时考虑应用条件与数据库策略。

### 风险与缓解

- 风险：某张表漏建策略，且恰好只经由租户池访问。
  缓解：迁移附带策略存在性测试，遍历业务表断言策略齐全。
- 风险：忘记开事务导致 `SET LOCAL` 未生效。
  缓解：仓储层只暴露接受 `&mut Transaction` 的函数，不开事务无法调用。
- 风险：管理池被误用到租户路由。
  缓解：路由装配时按分组注入，类型不同不可互换。

## 备选方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 仅应用层条件 | 实现最简单，无事务约束 | 依赖自觉与测试，漏写即越权 | 安全底线不能靠约定 |
| 仅 RLS | 数据库层强制 | 应用层仍可能用错角色；索引使用不直观 | 单一防线，缺少编译期约束 |
| 每租户独立 schema | 隔离直观 | 迁移与连接管理复杂度随租户数线性增长 | 300 租户规模下不值得 |
| 每租户独立数据库 | 隔离最强 | 运维成本极高 | 单人无法维护 |

## 验证方式

- 命令或检查项：
  - 以 A 租户身份访问 B 租户资源，断言返回 404。
  - 在未设置 `app.tenant_id` 的事务中查询业务表，断言返回空集。
  - 对含 `tenant_id` 的查询执行 `EXPLAIN`，断言命中复合索引。
- 观察指标：跨租户拒绝次数、RLS 策略覆盖率。
- 复核时间：M0 完成后一次；新增业务表时必须重跑策略测试。
