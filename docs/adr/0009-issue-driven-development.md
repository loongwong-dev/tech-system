# ADR-0009：以 Issue 作为开发任务的唯一来源

- 状态：Accepted
- 日期：2026-10-31
- 决策者：仓库维护者
- 相关：[Issue 驱动开发流程](../process/issue-workflow.md)、[AGENTS.md](../../AGENTS.md)

## 背景

开发由 AI 辅助完成，过程对维护者不可见：任务只存在于对话中，进度靠回忆，改动与需求的对应关系在会话结束后即丢失。这带来三个具体问题：

- 无法确认「当前正在做哪个任务」。
- 无法判断进度，只能等一次大提交后才知道结果。
- 无法追溯「为什么改这行」，因为提交信息只描述动作，不描述需求。

- 约束 1：单人维护，流程开销必须接近零。
- 约束 2：状态必须机器可读，既能被人查询，也能被代理读取。
- 不做什么：不引入外部项目管理工具，不维护手工进度表。

## 决策

1. 任务结构分三层：Milestone（阶段）、Epic（交付单元）、Task（原子任务）。
2. **所有开发都必须有对应 Issue**，包括一行修复。
3. 状态使用五个标签表达：`ready`、`in-progress`、`blocked`、`review`、`done`。
4. **全局同时只允许一个 `status:in-progress`**。
5. 代理在开工与收尾时必须各留一条评论：计划与交付。
6. 追溯链固定为 `需求章节 → Issue → 分支 → commit → PR → 代码`，commit 必须引用 Issue 编号。
7. 状态与进度全部从 Issue 派生，不维护手工进度表。

## 后果

### 正面

- 「现在在做什么」有唯一答案，且可被命令查询。
- 每次交付都有验证输出，黑盒被打开三个可审计窗口。
- 改动与需求、决策、文档形成可跳转的链条，半年后仍能还原上下文。

### 负面 / 代价

- 每个任务多出创建 Issue、两条评论、一次标签变更，约 5 分钟开销。
- 需要维护标签集合并在新仓库初始化。
- 代理必须遵守协议，否则流程退化为形式。

### 风险与缓解

- 风险：Issue 变成仪式，验收标准写得含糊。
  缓解：模板强制要求可执行的验收标准与明确非范围；不可执行的 Issue 不得进入 `ready`。
- 风险：任务过大，`in-progress` 长期不变。
  缓解：超过两天的任务必须拆分；Epic 承担长周期，Task 保持一天内。
- 风险：标签状态与实际不符。
  缓解：`check-trace.sh` 校验提交引用；PR 必须包含 `Closes #N`。

## 备选方案

| 方案 | 优点 | 缺点 | 未采用原因 |
| --- | --- | --- | --- |
| 只用提交信息描述任务 | 零开销 | 无进度视图，无验收标准，无法回溯需求 | 正是当前问题的成因 |
| 维护 `TODO.md` | 简单直观 | 与代码分离，容易过期，无状态机 | 会变成第二份真相 |
| 引入 Jira 等外部工具 | 功能完整 | 账户、配置、同步成本，单人过重 | 开销与收益不匹配 |
| GitHub Projects 作为主数据源 | 看板直观 | 视图与 Issue 状态容易不一致 | 只作为派生视图使用 |

## 验证方式

- 命令或检查项：`BASE_SHA=<base> bash scripts/check-trace.sh`；`gh issue list --label status:in-progress` 应始终返回 0 或 1 条。
- 观察指标：Issue 从 `in-progress` 到 `done` 的停留时间；`review` 退回 `in-progress` 的比例。
- 复核时间：第一个里程碑完成后，确认开销是否可接受。
