# 代码评审

合并前的评审范围、风险分级、阻断项与合并条件。

- **覆盖范围**：评审角色、风险分级、阻断项、评审者动作、PR 规模、合并条件。
- **不覆盖范围**：任务来源与状态流转见 [Issue 驱动开发流程](issue-workflow.md)；代码结构见 [代码规范](code-standards.md)。
- **状态**：已定，评审标准变化需同步 PR 模板与 `AGENTS.md`。

## 1. 原则

1. **评审对象是「是否满足 Issue 与约束」，不是风格。** 格式交给 rustfmt 与 clippy，命名与结构交给 CS 规则，人只看机器看不见的东西。
2. **未通过评审不得合并。** 包括文档改动。
3. **AI 不得自行合并 PR。** 合并是维护者的动作，不是作者的收尾步骤。
4. **评审必须实际运行。** 只读 diff 的评审等于没有评审。

## 2. 角色

| 角色 | 职责 | 能否合并 |
| --- | --- | --- |
| 作者（AI 或人） | 自检、开 PR、响应意见 | 否 |
| 评审者（维护者） | 按风险分级评审、运行验证、给出结论 | 是 |
| CI | 执行机器检查 | 否，但可阻断 |

单人仓库下 GitHub 不允许自我批准。落地方式是：**CI 全绿加维护者在 PR 中明确 Approve 后手动合并**，不使用机器人账号绕过。

## 3. 风险分级

评审深度按风险分级，避免文档改动也走全流程。

| 等级 | 涉及范围 | 评审要求 |
| --- | --- | --- |
| A | 认证与会话、租户隔离、配额扣减、数据删除、支付、AI 提示词与质量闸门 | 逐行阅读 + 本地运行 + 至少两条测试证据 + 越权路径检查 |
| B | 业务逻辑、接口形状、任务队列、渲染 | 逐行阅读 + 至少一条运行证据 |
| C | 文档、注释、格式、测试重构 | 浏览改动 + `check.sh docs` 通过 |

PR 创建时必须勾选等级。等级判断不清时按高一级处理。

## 4. 阻断项

任一条存在即 Request changes，不接受「后续修复」。

| 编号 | 阻断项 |
| --- | --- |
| CR-01 | 跨租户路径缺少测试，或测试未断言返回 404 |
| CR-02 | 请求路径出现 `unwrap` / `expect` |
| CR-03 | 错误被吞掉或丢失原因 |
| CR-04 | 破坏 API 契约且未升版本 |
| CR-05 | 「已验证」但没有命令与输出 |
| CR-06 | 无 Issue 关联，或缺少交付评论 |
| CR-07 | 业务代码净变更超过 400 行且未拆分 |
| CR-08 | 新增依赖未说明理由与替代方案 |
| CR-09 | 文档、CHANGELOG、ADR 未按影响更新 |
| CR-10 | 提交中出现密钥、真实个人信息或临时文件 |
| CR-11 | 测试被删除、跳过或被弱化以让 CI 变绿 |

## 5. 可跟进项

不阻断合并，但必须开 Issue 记录，不允许口头约定：

- 命名不理想、可提炼的重复、注释缺失。
- 性能优化与重构。
- 覆盖率缺口（P0 之外的用例）。

评审者应明确写下「不阻断，理由是什么」，避免作者误以为被默许忽略。

## 6. 评审者动作

按顺序执行，不要跳步：

1. 读 Issue 与验收标准，确认这次改动对应的需求。
2. 看 PR 的变更统计与风险等级，判断是否需要拆分。
3. **实际运行**：至少跑一次受影响路径；A 级必须跑完整流程。
4. 逐条核对第 4 节的阻断项。
5. 抽查测试是否真的有效：临时改坏一处实现，确认测试变红。
6. 给出结论：Approve、Request changes 或 Comment。

第 5 步是关键。大量测试「永远绿」，是因为断言的是实现细节或根本没有断言。

## 7. 作者自检

开 PR 前完成，未完成不进入评审：

- 验收标准逐条对照，逐条写证据。
- 审查自己的 diff，删除调试输出与临时文件。
- 确认没有超出 Issue 范围的内容。
- 确认 PR 描述包含改了什么、为什么、如何验证、风险与回滚。

## 8. PR 规模

| 净变更行数 | 处理 |
| --- | --- |
| ≤ 200 | 正常评审 |
| 200–400 | 需在 PR 中说明为何不能再拆 |
| > 400 | 拆分；机械改动（重命名、生成物、纯文档）除外 |

统计不含锁文件与生成物。大 PR 的问题不是好看与否，而是**评审会退化为浏览**。

## 9. 合并条件

全部满足才可合并：

1. CI 全绿，包括文档、链接、行数、密钥检查。
2. 至少一次维护者 Approve。
3. 第 4 节阻断项全部清零。
4. 所有评审会话已解决。
5. PR 正文包含 `Closes #N`，Issue 已有交付评论。
6. 分支基于最新 `main`，冲突已处理。
7. 迁移与部署影响已在描述中说明。

合并方式统一使用 squash，保持 `main` 线性且一条 PR 对应一条提交。

## 10. 记录

- 评审意见写在 GitHub Review 中，不留在聊天记录里。
- 已解决的问题不删除，保留上下文。
- 结论只允许三种：Approve、Request changes、Comment。

## 11. 反模式

| 反模式 | 后果 |
| --- | --- |
| 橡皮图章式 Approve | 阻断项被放过，问题延后暴露 |
| 只读 diff 不运行 | 无法发现「能编译但不工作」 |
| 用个人偏好阻断 | 评审变成审美争论 |
| 大 PR 一次审完 | 后三分之一基本没看 |
| AI 自审自合 | 评审机制整体失效 |
| 把可跟进项说成「以后再说」 | 技术债没有记录，等于没提 |
