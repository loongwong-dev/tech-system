# 部署与运维

单机部署的拓扑、备份、发布、可观测性与日常维护。

- **类型**：项目运维
- **覆盖范围**：服务器规格、容器编排、数据库参数、备份恢复、发布回滚、监控告警、磁盘策略、成本。
- **不覆盖范围**：CI 工作流见 [CI/CD 与质量门禁](../ci-cd.md)；安全细节见 [认证与安全](../design/platform/authentication.md)。
- **状态**：已定，拓扑或流程变更时同步更新。

## 1. 服务器

| 项 | 值 |
| --- | --- |
| 规格 | 2 vCPU / 4GB / 80GB SSD |
| 区域 | 境内（ICP 备案要求） |
| 系统 | Linux LTS，仅开放 22 / 80 / 443 |
| 时区 | UTC，展示层转换 |

不部署独立监控栈。可观测性由外部探针、错误上报与管理端健康页承担，详见第 6 节。

## 2. 容器编排

单机 Docker Compose，四个服务：

| 服务 | 职责 | 资源限制 |
| --- | --- | --- |
| `caddy` | TLS、静态资源、反向代理、安全头 | 128MB |
| `api` | HTTP、SSE、会话 | 1.5 CPU / 1GB |
| `worker` | 任务队列、定时任务、图片渲染 | 1.5 CPU / 1GB |
| `postgres` | 数据库 | 1 CPU / 2GB |

`api` 与 `worker` 使用**同一镜像**、不同启动命令：

```text
./app serve     # api
./app worker    # worker
```

分开的理由：渲染是 CPU 密集型，混在 API 进程里会让请求延迟抖动；worker 崩溃重启不应带走在线会话；两者可以独立限制资源。

数据卷只挂两个：PostgreSQL 数据目录、图片缓存目录。其余容器无状态。

## 3. 数据库参数

按 4GB 内存配置：

```text
shared_buffers = 1GB
effective_cache_size = 3GB
work_mem = 16MB
maintenance_work_mem = 256MB
max_connections = 50
random_page_cost = 1.1
```

`max_connections` 留余量给迁移、备份与临时排障。连接池总量控制在 20 以内：

| 用途 | 上限 |
| --- | --- |
| api 租户池 | 10 |
| api 管理池 | 5 |
| worker 管理池 | 5 |

## 4. 备份与恢复

采用高频全量备份，不启用 WAL 归档。

| 项 | 值 |
| --- | --- |
| 频率 | 每小时 `pg_dump -Fc` |
| 本地保留 | 48 小时 |
| 每日快照 | 保留 14 天 |
| 异地 | 加密后上传对象存储 |
| 图片 | 不备份，属于可重建缓存 |

理由：数据库在目标规模下远小于 1GB，每小时全量的存储成本可忽略；PITR 需要额外工具链与更长的恢复流程，单人维护不划算。

### 恢复演练

未演练的备份等于没有备份。`scripts/restore-drill.sh` 每月执行一次：

```text
1. 启动临时 PostgreSQL 容器
2. 拉取最近一份 dump 并恢复
3. 执行校验查询：各表行数、最近一条反馈时间、RLS 策略数量
4. 记录恢复耗时
5. 销毁临时容器
```

恢复耗时记入本文的「演练记录」，超过 2 小时需要分析原因。

## 5. 发布与回滚

```text
CI 构建镜像（tag = git sha）→ 推送 registry → 服务器拉取
→ 执行迁移（一次性容器）→ 重启 api → 重启 worker
```

| 环节 | 规则 |
| --- | --- |
| 迁移 | 发布前独立执行，失败即中止 |
| 停机 | 单实例重启约 5–10 秒，接受 |
| 回滚 | 切回上一镜像 tag，**不执行逆向迁移** |
| 迁移兼容 | 扩展再收缩：新列先可空、双写一个版本、再删旧列 |
| 版本固定 | typst、PostgreSQL、Caddy 锁定小版本 |

回滚不跑逆向 DDL 是硬规则。任一步逆向迁移都可能造成数据丢失。

## 6. 可观测性

三层，不引入 Prometheus 与 Grafana：

| 层 | 内容 |
| --- | --- |
| 外部探针 | 每分钟请求 `/healthz`，连续 2 次失败告警 |
| 错误上报 | Sentry 免费档，按 issue 去重 |
| 管理端健康页 | 聚合业务级健康信息，登录后可见 |

`/healthz` 只检查进程存活；`/readyz` 检查数据库连接与队列可用性。

### 健康页展示项

| 指标 | 告警阈值 |
| --- | --- |
| 数据库连接 | 取不到即红 |
| 队列最老 `pending` 年龄 | > 5 分钟 |
| 24 小时渲染失败率 | > 5% |
| 24 小时 AI 失败率 | > 10% |
| 磁盘使用率 | > 80% |
| 最后成功备份时间 | > 2 小时 |
| 最近 24 小时 5xx 数 | > 0 标黄 |

目标是**不登服务器就能判断系统是否正常**。

### 历史趋势

不使用时序数据库，改为每日汇总：

```sql
CREATE TABLE daily_stats (
  day    date NOT NULL,
  metric text NOT NULL,
  value  bigint NOT NULL,
  PRIMARY KEY (day, metric)
);
```

由 worker 的定时任务写入，指标包括生成份数、分享数、AI 失败、渲染失败、注册数、配额耗尽次数。一天一行，不膨胀。

告警渠道使用邮件或企业微信机器人。

## 7. 磁盘与图片生命周期

图片文件增长很快：

```text
300 个付费用户 × 200 份/月 = 60,000 份/月
60,000 × 200KB ≈ 12GB/月
```

**图片是缓存，不是数据。** 同一份反馈、同一模板版本、同一 typst 版本，渲染结果确定可重现。因此：

| 环节 | 策略 |
| --- | --- |
| 生成 | 按 `hash(view + template_version)` 缓存 |
| 保存期限 | 30 天 |
| 过期 | 删除文件，链接同时过期 |
| 需要重看 | 按需重新渲染 |
| 备份 | 只备份数据库与模板 |

链接有效期 7 天，短于图片保留期，两者不会冲突。

## 8. 成本

| 项 | 估算 |
| --- | --- |
| 2C4G / 80GB 云服务器 | ¥100–150/月 |
| 对象存储备份 | ¥1–5/月 |
| 域名 | ¥50/年 |
| TLS | 免费 |
| Sentry | 免费档 |
| AI 调用 | ¥1–10/月 |
| 合计 | 约 ¥100–150/月 |

按 19 元/月定价，覆盖固定成本需要 6–8 个付费用户。用户量上来之前，服务器层面的优化都不值得做。

## 9. 接受的风险

| 风险 | 影响 | 为何接受 |
| --- | --- | --- |
| 单机宕机 | 全站不可用 | 与 99% 可用性目标一致，重启即恢复 |
| 磁盘写满 | 服务异常 | 80% 告警 + 图片 TTL |
| 误删数据 | 最多丢 1 小时 | 每小时备份 |
| 数据库损坏 | 约 2 小时恢复 | 已演练；规模不值得上主从 |
| 监控能力有限 | 故障发现依赖探针与管理端 | 单人维护的取舍，后续按需升级 |
